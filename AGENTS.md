# AGENTS.md — openshift/custom-metrics-autoscaler-operator

AI-specific guidance for working in the OpenShift downstream fork of
[kedacore/keda-olm-operator](https://github.com/kedacore/keda-olm-operator). For
contribution conventions, the PR workflow, and the full make target reference, see
[CONTRIBUTING_OPENSHIFT.md](CONTRIBUTING_OPENSHIFT.md).

## Project Overview

This repo is the **Custom Metrics Autoscaler operator** for OpenShift: the
OLM-managed controller that installs and configures the operands, which are
OpenShift's distribution of [KEDA](https://keda.sh). Cluster administrators install
this operator from OperatorHub and then create a single `KedaController` custom
resource; the operator turns that spec into a running KEDA installation.

The operator owns exactly **one** CRD: `KedaController` (`keda.sh/v1alpha1`). The CRDs
that users actually write autoscaling rules against — `ScaledObject`, `ScaledJob`,
`TriggerAuthentication`, `ClusterTriggerAuthentication`, `CloudEventSource`,
`ClusterCloudEventSource`, `HTTPScaledObject`, `InterceptorRoute` — belong to the
operands. This repo only ships their manifests inside the OLM bundle. Do not look for
Go types for them here; there are none.

### The operands this operator deploys

One `KedaController` can result in up to six deployed controllers, spread across two
operand repos. Which ones exist depends on the spec — the HTTP Add-on trio is only
deployed when `spec.httpAddon.enabled` is set.

| Operand | Deployment | Repo |
|---------|------------|------|
| KEDA operator | `keda-operator` | [openshift/kedacore-keda](https://github.com/openshift/kedacore-keda) |
| Metrics adapter | `keda-metrics-apiserver` | [openshift/kedacore-keda](https://github.com/openshift/kedacore-keda) |
| Admission webhooks | `keda-admission` | [openshift/kedacore-keda](https://github.com/openshift/kedacore-keda) |
| HTTP Add-on operator | `keda-add-ons-http-operator` | [openshift/kedacore-http-add-on](https://github.com/openshift/kedacore-http-add-on) |
| HTTP Add-on interceptor | `keda-add-ons-http-interceptor` | [openshift/kedacore-http-add-on](https://github.com/openshift/kedacore-http-add-on) |
| HTTP Add-on scaler | `keda-add-ons-http-scaler` | [openshift/kedacore-http-add-on](https://github.com/openshift/kedacore-http-add-on) |

For the product overview and the full `KedaController` spec reference, see
[README.md](README.md). For user-facing documentation, see
[Custom Metrics Autoscaler on OpenShift](https://docs.openshift.com/container-platform/latest/nodes/cma/nodes-cma-autoscaling-custom.html)
and the [KEDA documentation](https://keda.sh/docs/latest/).

### The most important thing to understand

The operator does **not** template the operands with Helm or with Kustomize overlays at
deploy time. It stores the operands' full release manifests as static YAML in
[`resources/`](resources/), parses them at startup, and then applies a chain of
`manifestival` transformer functions to mutate them in memory according to the
`KedaController` spec before applying them to the cluster.

This means: **if you want to make a new operand setting configurable, you add a field
to the `KedaController` API and a transformer function — you do not edit
`resources/keda.yaml`.** That file is imported verbatim from an upstream KEDA release
and is overwritten wholesale on the next release bump.

The manifests are read from the **filesystem at runtime**, not compiled in with
`go:embed`. See pitfall 3 for the surprising consequence.

## Upstream / Downstream Relationship

This repo tracks `kedacore/keda-olm-operator` on the `main` branch. There are no
release branches in active use; fixes and releases are made from `main`.

### What is downstream-only

- `OWNERS` — OpenShift approver list
- `.ci-operator.yaml` — OpenShift CI build root config
- `Dockerfile.ci` — the operator image built by OpenShift CI and shipped downstream
- `bundle.Dockerfile.ci` and `bundle-previous.Dockerfile.ci` — bundle images for CI
- `hack/cma-generate-csv.sh`, `hack/cma-check-all-csv.sh`, `hack/cma-verify-history.sh`
- `keda/*/manifests/cma.v*.clusterserviceversion.yaml` — the CMA-branded CSVs
- `must-gather/`
- `CONTRIBUTING_OPENSHIFT.md`, `AGENTS.md`, `.coderabbit.yaml`

### What is upstream

Everything else: the API types, the controllers, the transformer library, the
`resources/` manifests, `config/`, `bundle/`, the Makefile, `Dockerfile`,
`bundle.Dockerfile`, and `.github/workflows/`. Prefer contributing fixes and features
upstream and carrying them here with an `UPSTREAM: <PR number>:` prefix, so they drop
out of the carry set once the rebase catches up. Every file you patch downstream is a
file someone has to re-apply during the next rebase.

### Rebase cycle

- `UPSTREAM: <drop>:` commits are discarded
- `UPSTREAM: <carry>:` commits are re-applied
- `UPSTREAM: 1234:` commits are dropped if upstream PR 1234 is now included, otherwise re-applied

## Architecture: What Is Not Obvious

### Reconciliation flow

1. A `KedaController` CR is created. **Only** a CR named `keda` in the namespace where the operator is installed does anything; others are ignored. There is intended to be exactly one per cluster.
2. On startup, a background goroutine (`ensureKedaController`) creates a default `KedaController` if none exists. This is why the operands appear without the administrator doing anything. It can be suppressed with the `keda-olm-operator/create-default-controller=skip` annotation on the namespace — the e2e OLM targets rely on this.
3. The reconciler loads the stored operand manifests from disk and splits them at parse time into independent buckets: `general` (ServiceAccount, NetworkPolicies), `controller` (KEDA operator Deployment), `metrics` (metrics adapter + APIService), `webhooks` (admission webhooks), and `monitoring` (ServiceMonitor/PodMonitor). Each bucket is applied and deleted independently.
4. A chain of `manifestival` transformers rewrites namespaces, images, log levels, resource requests, tolerations, affinity, volumes, certificates, and TLS settings based on the spec.
5. Status is written back to the `KedaController`, per component.

### The operand images are injected, not hardcoded

The image references baked into `resources/keda.yaml` are overridden at runtime from
environment variables on the operator Deployment: `KEDA_OPERATOR_IMAGE`,
`KEDA_METRICS_SERVER_IMAGE`, `KEDA_ADMISSION_WEBHOOKS_IMAGE`,
`KEDA_HTTP_ADDON_OPERATOR_IMAGE`, `KEDA_HTTP_ADDON_INTERCEPTOR_IMAGE`,
`KEDA_HTTP_ADDON_SCALER_IMAGE`.

Downstream, `hack/cma-generate-csv.sh` rewires these to OSBS-style `RELATED_IMAGE_1`,
`RELATED_IMAGE_2`, and `RELATED_IMAGE_3` pullspecs in the CSV, and OpenShift CI
substitutes `CMA_OPERAND_PLACEHOLDER_1/2/3` for the freshly built operand images. If
you add a new operand image, all three layers need updating — the env var, the CSV
generator, and the CI substitution list in
[openshift/release](https://github.com/openshift/release/tree/master/ci-operator/config/openshift/custom-metrics-autoscaler-operator).

### OpenShift-specific behavior is conditional

`util.RunningOnOpenshift` gates a meaningful amount of logic. The ConfigMap and Secret
controllers exist only to react to OpenShift's service-CA and serving-cert injection
for the metrics apiserver: when the injected CA bundle or TLS cert changes, they
compute a checksum, store it in the `KedaController` status
(`ConfigMapDataSum` / `SecretDataSum`), and restart the metrics server pod. The
operator also watches the cluster-scoped `APIServer` config resource to pick up the
cluster's centralized TLS security profile and translate it into cipher and minimum
version settings for the operands.

### There are three CSVs, and they are not the same thing

1. `config/manifests/bases/keda.clusterserviceversion.yaml` — hand-maintained template.
2. `bundle/manifests/keda.clusterserviceversion.yaml` — generated by `make bundle` from the above. Upstream-branded, package `keda`. Used for local and upstream testing.
3. `keda/<version>/manifests/cma.v<version>.clusterserviceversion.yaml` — generated by `hack/cma-generate-csv.sh` from the *upstream-style* per-release CSV. CMA-branded, package `openshift-custom-metrics-autoscaler-operator`. **This is what actually ships to OpenShift customers.**

`bundle.Dockerfile.ci` packages the newest `keda/<version>/` directory and deletes the
`keda.*` CSV so only the `cma.*` one remains. `bundle-previous.Dockerfile.ci` packages
the second-newest, which is what the upgrade e2e job upgrades *from*; this works only
because the newest CSV's `replaces` field points at it.

## Common Pitfalls

1. **Add an `UPSTREAM:` prefix to every commit.** Every non-upstream commit needs `UPSTREAM: <carry>:`, `UPSTREAM: <drop>:`, or `UPSTREAM: 1234:`. The `cma-verify-history` CI job enforces this. This is the single most common reason a PR here fails CI.

2. **Never hand-edit `resources/keda.yaml` or `resources/keda-http-addon.yaml`.** They are imported verbatim from upstream operand releases by `hack/relprep.sh` and `hack/http-add-on-relprep.sh`, and any edit is silently destroyed on the next release bump. To change operand behavior, add a `KedaController` field plus a transformer in `internal/controller/keda/transform/`, or fix it in the operand repo.

3. **The operand manifests are loaded from disk by their compile-time path, so moving `resources/` breaks the image.** `resources/resources_handler.go` locates the YAML with `runtime.Caller(0)`, which returns the *build-time* source path, and then reads the files from that directory at runtime. There is no `go:embed`. This is why `Dockerfile` copies them to `/workspace/resources/` — matching the builder's `WORKDIR` — and why `Dockerfile.ci` creates a symlink (`ln -s /resources /src/cma-operator/app/resources`) rather than just copying them somewhere convenient. If you move or rename the `resources/` directory, change the builder `WORKDIR`, or add a new manifest file, you must update both Dockerfiles or the operator will panic at startup in the container while working fine under `make run`.

4. **Never hand-edit `bundle/`.** It is entirely generated by `make bundle`. Change `config/manifests/bases/keda.clusterserviceversion.yaml` and regenerate.

5. **Never hand-edit the `cma.v*.clusterserviceversion.yaml` files.** They come from `hack/cma-generate-csv.sh`. If the CMA CSV needs to change, change the `jq` transformation in that script and regenerate; `make cma-check-all-csv` will fail otherwise, and it checks every version from 2.19.0 onward.

6. **`make bundle` and `make deploy` mutate tracked files in `config/`.** Both run `kustomize edit set image` and `kustomize edit add label`, which write to `config/manager/kustomization.yaml` and `config/default/kustomization.yaml`. Check `git status` after running them and do not commit the churn unintentionally.

7. **The test targets are not read-only either.** `make test`, `make test-functionality`, `make test-deployment`, and `make test-audit` all depend on `manifests generate fmt vet`, so they can rewrite generated files and reformat code as a side effect.

8. **The lint target is `make golangci`, not `make lint`.** There is also no `make verify`; check generated-file drift with `make manifests generate && git diff --exit-code`.

9. **Only `keda.sh_kedacontrollers.yaml` is generated by controller-gen.** The other CRDs in `config/crd/bases/` are operand CRDs copied in from upstream releases. Running `make manifests` will not regenerate them, and editing them by hand is wrong for the same reason as pitfall 2.

10. **Do not touch the Go module path.** It is `github.com/kedacore/keda-olm-operator`, not a path matching this repo's name. It is also the `canonical_go_repository` in our CI config; renaming it breaks the build and the rebase.

11. **`vendor/` is checked in.** After changing `go.mod`, run `go mod tidy && go mod vendor` and commit the vendor churn as a separate commit from the logic change.

12. **Deployment selectors are immutable, and breaking them breaks upgrades.** An `app.kubernetes.io/version` label previously leaked into a Deployment's `matchLabels` and broke OLM upgrades; `hack/cma-generate-csv.sh` now strips it, and the `make e2e-olm-upgrade-build` target does the same for its synthetic CSV. Be very careful with label changes that could reach a selector.

13. **Our CI is Prow, not GitHub Actions.** The workflows in `.github/workflows/` come from upstream. What gates a merge here is the Prow job set: `gofmt`, `govet`, `cma-check-all-csv`, `cma-verify-history`, `security`, `cma-e2e-aws-ovn`, `cma-e2e-gcp-ovn`, and `cma-e2e-upgrade-aws`.

14. **CI is not the release build.** OpenShift CI builds `Dockerfile.ci` for testing; Konflux ([openshift/custom-metrics-autoscaler-pipelines](https://github.com/openshift/custom-metrics-autoscaler-pipelines)) builds what ships to customers. A Dockerfile change that passes CI can still be wrong for the shipped image.

15. **`Dockerfile.ci` is unusual on purpose.** It manually vendors `controller-tools`, `mock`, and `protobuf` sources for OSBS/Cachito compliance, and patches the PodMonitor name from `keda-olm-operator` to `custom-metrics-autoscaler-operator`. Do not "clean up" these steps without understanding why they exist.

16. **Never delete user CRs or operand CRDs on uninstall.** The operand CRDs are installed unconditionally, including the HTTP Add-on ones even when the add-on is disabled, specifically so that removing the operator never destroys a user's `ScaledObject`s.

## Human-in-the-Loop Triggers

Stop and consult a human before:

- **Changing the `KedaController` API** (`api/keda/v1alpha1/`) — API changes are user-visible and permanent; removing or repurposing a field breaks existing installations
- **Changing RBAC** (`config/rbac/`, `+kubebuilder:rbac` markers) — this operator is highly privileged and RBAC changes need security review
- **Changing the CSV, the bundle layout, or the `replaces` chain** — these govern OLM upgrades, which have broken before and are painful to fix in the field
- **Changing `hack/cma-generate-csv.sh`** — it determines what ships to customers
- **Changing Dockerfiles or base images** — affects both the CI image and the Konflux release build
- **Performing a release bump** (`hack/relprep.sh`) — a multi-step process documented in [RELEASE-PROCESS.md](RELEASE-PROCESS.md), with downstream steps beyond it
- **Modifying the upstream/downstream boundary** — deciding that a change should be carried rather than sent upstream
- **Anything that has to change in the operand repo too** — coordinate the two PRs

## Paired Changes

| If you change... | Also update... |
|------------------|----------------|
| `api/keda/v1alpha1/*_types.go` | `make generate && make manifests`, and the `KedaController` spec docs in `README.md` |
| A `+kubebuilder:rbac` marker | `make manifests`, then re-check the CSV permissions |
| `config/manifests/bases/keda.clusterserviceversion.yaml` | `make bundle`, and consider whether `hack/cma-generate-csv.sh` needs the same change |
| `hack/cma-generate-csv.sh` | Regenerate every affected `cma.v*` CSV and run `make cma-check-all-csv` |
| A new operand image | The `KEDA_*_IMAGE` env var, `hack/cma-generate-csv.sh` `RELATED_IMAGE_*` wiring, and the CI `substitutions` in openshift/release |
| A new `KedaController` spec field | A transformer in `internal/controller/keda/transform/`, its unit test, and the `README.md` spec reference |
| The `resources/` directory layout, or a Dockerfile builder `WORKDIR` | Both `Dockerfile` and `Dockerfile.ci`, which hardcode the compile-time manifest path (see pitfall 3) |
| `go.mod` | `go mod tidy && go mod vendor`, committed separately |
| The operand version | `hack/relprep.sh <version>`, which touches `resources/`, `config/crd/bases/`, `keda/<version>/`, and `go.mod` together |
| Anything affecting OLM upgrade behavior | Run the five-target upgrade sequence in [CONTRIBUTING_OPENSHIFT.md](CONTRIBUTING_OPENSHIFT.md#olm-upgrade-test-sequence) |
